How it works

Every machine. Every shot. Every stop.

A small laser watches each moulding machine and counts what it makes, automatically, all day, all night. When a machine stops, the system notices, times it, and asks the operator why. No clipboards, no guessing, and nothing wired into the machine.

The problem it solves

Nobody can say exactly how much a machine actually ran yesterday, or where the lost hours went. By the time it shows up in the month-end numbers, the reason has been forgotten.

📋

Counted by hand

Someone writes production on a sheet, at the end of a shift, from memory. Nobody blames them, it's the only tool they've been given.

🕳️

Stops vanish

A machine sits dead for forty minutes at 2am. Nothing records it, so it never happened, so it happens again next week.

🤷

No "why"

Even when downtime is known, the reason isn't. You can't fix a problem you can't name.

How a laser counts production

A moulding machine squeezes a mould shut, fills it, cools it, then opens and drops the part out. Over and over. That movement is the only thing the sensor needs to see.

📏

It learns the machine

On power-up it watches the mould move back and forth a few times and works out the machine's own range of travel. Nobody configures anything.

🔁

Shut → open → shut

That's one part made. The time between two of them is the cycle time, and if that starts creeping up, the machine is struggling.

⏱️

Nothing moving

No movement for a few minutes means the machine has stopped, and the clock starts running.

Not every pause is downtime

Calling every eight-second hiccup "downtime" produces numbers nobody trusts. So a stop is graded by how long it lasts, and each machine has its own thresholds, a twelve-second cycle and a forty-five-second cycle do not mean the same thing by "stopped".

The part only a person can answer

The sensor knows a machine stopped and for how long. It has no idea why. Only the person standing there knows that, so it asks them, in the simplest way that will actually get used.

A printed code on the machine Laminated, cable-tied where the operator stands. That's the entire installation.
They scan it with their own phone No app to install, no login, no training. It opens straight to that machine.
One tap Material issue · Machine fault · Scheduled or unscheduled mould change · Maintenance · Order complete. Done in three seconds, with oily hands.
The reason sticks to the event From then on the report doesn't say "41 minutes lost". It says "41 minutes lost to material shortage".

Why it can go on any machine

🔌

Nothing wired in

The laser doesn't touch the machine and doesn't need its permission. No electrician, no PLC access, no warranty argument.

🏭

Any age, any brand

If the mould moves, it can be counted. A machine from 1995 works exactly as well as one from last year.

➕

One at a time

Start with one machine. Add the next whenever you like, nothing has to be rebuilt to make room.

Under the bonnet

Technical notes, for whoever maintains this

The chain. An M5Stack AtomS3 with a time-of-flight laser measures platen distance at 10 Hz. It learns the stroke (five direction changes, minimum 200 mm of travel), sets closed and open thresholds at 35% and 55% of that stroke, and counts one shot per CLOSED → OPEN → CLOSED. It publishes JSON twice a second over MQTT.

One firmware for every sensor. A sensor does not know which machine it is on. It reports the MAC address burned into its own chip and is paired to a machine on the Sensors page, so moving one is a dropdown, not a laptop and a USB cable, and the wrong file can never be flashed onto the wrong machine.

Two failures that were found and guarded. The device counts in its own memory, so the network is the weak point. If wifi drops and the machine keeps producing, the missed run is reconstructed on reconnect and logged as reconstructed rather than measured. If the device power-cycles its counter restarts at zero, which naively reads as a part being made, and would close an open downtime event with a false "recovered" while the machine was still standing still. Both are guarded and covered by tests.

One setting to check on the first real machine. The learning routine only counts movement when two consecutive readings differ by more than MOVE_DELTA_MM. The value the program originally shipped with is the only one tested that can fail to arm at all, it works on a desk, where a hand waved past the sensor jumps hundreds of millimetres between readings, but a platen moving smoothly may not. It is now set lower, which armed in every case tested. Confirm on the first machine that the sensor leaves LEARNING within about two minutes.

Numbers that are still estimates. Expected cycle times are provisional until somebody times the machines, they set when a stop counts as downtime and how many units a stop cost. Cavities per mould default to 1, so "units not made" currently under-states rather than invents.

Talking to what already exists. The production table matches the schema the existing Node-RED flows write to, column for column, and the HTTP fallback route is the same path, so an existing flow can be pointed at this without being rewritten.
